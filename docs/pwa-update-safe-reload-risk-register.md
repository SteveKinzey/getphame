# Get Phame PWA Update Notice: Risk Register and Approved Mitigations

**Status:** Approved implementation constraints
**Scope:** Version-aware PWA update notice, user-controlled reload, service-worker migration, and administrator diagnostics.

## Executive Decision

Get Phame will implement a **detect-first, user-controlled** update flow. A newly deployed version may create a persistent, non-modal notice, but it must never reload a page automatically. The control plane is the platform deployment version endpoint; the service worker is a secondary broadcast mechanism rather than a replacement for page-level detection.

> **Mandatory safety invariant:** A browser reload or a waiting-worker activation may occur only after an explicit current-tab user action that passes the active-work safety checks. A deployment, timer, focus event, or service-worker message can never cause a reload on its own.

The current code confirms three baseline facts that shape the implementation: `/sw-v27.js` has an unconditional install-time `skipWaiting()` and cache-wide cleanup, `main.tsx` has the authoritative `/sw-v27.js` registration, and the unmounted legacy `AppContext` still contains a second `/sw.js` registration. The v28 migration will retire the second registration and tighten the worker lifecycle behavior without modifying `sw-v27.js`, preserving safety for already-installed clients.

| Worker activation | An unconditional `skipWaiting()` activates a new worker while another tab is still working, and `clients.claim()` changes that tab’s controller or clears its offline cache. | **Do not call `skipWaiting()` during `sw-v28.js` installation.** Retain `clients.claim()` only after normal activation. Support `SKIP_WAITING` only for `registration.waiting`, after a user action, and only when the waiting worker confirms that the requesting tab is the sole in-scope window client. Keep `sw-v27.js` unchanged. | Source-contract test proves no install-time `skipWaiting()` in v28, no message to an active controller, and multi-tab waiting-worker refusal. |
| Controller-change race | A listener attaches after a waiting worker activates, or a controller never changes, leaving a disabled control or repeat reload. | Attach a one-shot `controllerchange` listener **before** posting `SKIP_WAITING`; remove it after success or a bounded timeout. A timeout moves to a non-destructive failed state and never retries automatically. | Unit test covers listener ordering, timeout cleanup, single reload, and no retry loop. |
| Path-version bootstrap gap | Existing v27 clients cannot run the new detector until their next normal navigation, so the first release cannot notify already-open v27 pages. | Treat v28 as a bootstrap release. ## Lifecycle Decision Details

The service-worker lifecycle intentionally separates installation, activation, and client control. An installing worker normally waits while an existing worker controls pages; `skipWaiting()` overrides that wait, while `clients.claim()` lets an activated worker take control of matching clients.[1] [2] The worker migration therefore removes install-time `skipWaiting()` from v28 rather than repeating the v27 behavior.

This design does not dilute the product requirement to preserve offline support. A normal user-selected reload fetches the updated app shell through the existing network-first strategy. The new versioned worker may remain in `registration.waiting` until older tabs close; that is a safe, observable state, not an error. A later explicit action can use the waiting-worker path only if no peer tab would be affected. The browser API expressly exposes `registration.waiting` for this purpose.[3]

## Implementation Gates

The implementation must not advance to release unless all of the following statements are true.

1. `sw-v27.js` remains byte-for-byte unchanged and `/sw-v28.js` is the only registration URL in `main.tsx`.
2. No v28 code performs an unconditional install-time `skipWaiting()` or posts `SKIP_WAITING` to `navigator.serviceWorker.controller`.
3. The version endpoint is excluded from all cache paths and a failed fetch cannot show an update notice.
4. A reload has one explicit user origin and one reload attempt per target version per browser session.
5. A pending mutation blocks update; a dirty registered form requires a loss-confirmation decision.
6. All seven catalogs expose the same `versionUpdate` key shape, and the i18n and worker cache versions are aligned.
7. Administrator diagnostics are current-tab only, role-gated, localized, and non-sensitive.
8. The bootstrap limitation, multi-tab behavior, offline behavior, and no-service-worker fallback are documented in the release evidence.
